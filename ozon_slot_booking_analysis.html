1. Краткое резюме проекта

Проект представляет собой разработку Telegram-бота для автоматизации процесса мониторинга и бронирования временных слотов на складах маркетплейса Ozon. Основная цель — решить проблему дефицита доступных слотов для поставок товаров продавцами.

🎯 Целевая аудитория

  • Продавцы на маркетплейсе Ozon, работающие по схеме FBO (Fulfillment by Ozon)
  • Крупные поставщики с регулярными поставками на несколько складов
  • Логистические компании, работающие с Ozon
  • Малый и средний бизнес с объёмом поставок от 10 SKU

⚠️ Важное предупреждение от рынка

Использование ботов для отслеживания свободных слотов легально, но использование ботов для автоматического бронирования рискованно. Маркетплейсы могут обнаружить автоботов, что может привести к блокировке аккаунта продавца.

Рекомендация: Разрабатывать бота как инструмент мониторинга с уведомлениями, позволяя пользователю самостоятельно принимать решение о бронировании.

3. Постановка задачи

3.1. Проблема

  • Слоты на складах Ozon разбираются за секунды после появления
  • Продавцы тратят часы на ручной мониторинг
  • Пропущенный слот = задержка поставки = потеря продаж
  • Отсутствие единого удобного интерфейса для управления поставками

3.2. Решение

Telegram-бот, который:

  1. Мониторит доступность слотов 24/7 через Ozon Seller API
  2. Мгновенно уведомляет пользователя о появлении подходящих слотов
  3. Предоставляет удобный интерфейс для настройки параметров мониторинга
  4. (Опционально) Автоматически бронирует слоты при соблюдении условий
  5. Ведёт историю бронирований и аналитику

4. Функциональные требования

4.1. Основной функционал (MVP)

Регистрация и авторизация

  • Регистрация через Telegram (автоматически при старте бота)
  • Подключение Ozon Seller API ключей (Client ID + API Key)
  • Проверка валидности ключей
  • Хранение токенов в зашифрованном виде

Настройка мониторинга

  • Выбор складов для мониторинга (список доступных складов из API)
  • Установка предпочитаемых дат (от-до)
  • Выбор типа поставки (короб, монопаллет, смешанная паллета и т.д.)
  • Настройка минимального лимита приёмки
  • Включение/выключение "тихих часов"

Мониторинг слотов

  • Периодический опрос Ozon API (каждые 30-60 секунд)
  • Обнаружение новых доступных слотов
  • Мгновенное уведомление пользователя
  • Отображение деталей слота (дата, время, склад, лимит)

Уведомления

  • Уведомления о найденных слотах с кнопками быстрых действий
  • Уведомления об изменении статуса бронирования
  • Ежедневные дайджесты с аналитикой

Детальный пользовательский сценарий (User Journey)

🚀 Шаг 1: Начало работы

  1. Пользователь открывает приложение в Telegram
  2. На главной странице отображается баланс бронирований
  3. Пользователь нажимает "Мои кабинеты"
  4. Добавляет первый магазин OZON:
    • Client ID (идентификатор продавца)
    • API key с ролью Supply order
  5. Система проверяет валидность ключей через Ozon API
  6. При успехе кабинет добавляется, при ошибке показывается сообщение

⚠️ Важно: Получение API ключа

Для получения API ключа с ролью Supply order:

  1. Зайти в личный кабинет Ozon → Настройки → API ключи
  2. Создать новый ключ
  3. Обязательно выбрать роль "Supply order"
  4. Скопировать Client ID и API Key

Роль Supply order позволяет получать информацию по поставке FBO и работать со слотами.

📦 Шаг 2: Работа с поставками

  1. Создание черновиков поставок:
    • Пользователь создает черновики поставок в личном кабинете Ozon (не в боте)
    • Выбирает склады отгрузки и направления
    • Товарный состав должен быть согласован
    • Поставка должна находиться в статусе "Черновик"
  2. Синхронизация с ботом:
    • Пользователь переходит в раздел "Поставки" в боте
    • Бот загружает список заказов из OZON API
    • Отображает все черновики поставок
  3. Использование фильтров:
    • По магазинам: Все магазины / конкретные магазины
    • По статусу: Все заказы / В поиске / Слот найден

⏰ Шаг 3: Настройка удобных слотов

  1. Пользователь выбирает заказ из списка
  2. Нажимает кнопку "Редактировать"
  3. Указывает до 5 удобных временных промежутков для поставки:
    • Дата поставки
    • Временной диапазон (например, 9:00-12:00)
    • Можно выбрать несколько дней и время
  4. Нажимает "Сохранить настройки"
  5. Система переводит заказ в статус В поиске
  6. Автоматический поиск:
    • Бот начинает периодический опрос Ozon API
    • Проверяет доступность слотов по заданным параметрам
    • При нахождении подходящего слота — автоматически бронирует
  7. Уведомление:
    • Пользователь получает Telegram уведомление об успешном бронировании
    • Указывается дата, время и склад
    • Списывается 1 бронирование с баланса
    • Бот прекращает отслеживание этой поставки
    • Статус меняется на Слот найден
  8. Пользователь видит забронированный слот в личном кабинете Ozon

💳 Шаг 4: Покупка дополнительных бронирований

  1. Когда бронирования заканчиваются, пользователь получает уведомление
  2. Переходит в раздел "Тарифы"
  3. Выбирает подходящий тарифный план
  4. Оплачивает через:
    • T-Pay (Telegram платежи)
    • СБП (Система быстрых платежей)
    • Яндекс.Пэй
    • Банковские карты
  5. После оплаты бронирования доступны мгновенно
  6. Баланс обновляется на главной странице

💡 Важные нюансы работы с бронированиями

  • Поиск бесплатный: Бот может искать слоты бесконечно долго без списания средств
  • Списание только за результат: Бронирование списывается только когда бот успешно забронировал слот
  • Продление срока: При покупке новых бронирований до окончания текущего периода:
    • Старые бронирования сохраняются
    • Срок продлевается на 30 дней с момента новой покупки
    • Работает как у операторов связи с минутами
  • Множественные поставки: Если создать 50 поставок и бот найдет слоты для всех — спишется 50 бронирований
  • Рекомендация: Создавайте поставки разумно, контролируйте количество активных отслеживаний

5.2. Микросервисная vs Монолитная архитектура

✅ Рекомендуемый подход: Модульный монолит

Для MVP и средней нагрузки (до 10,000 пользователей)

  • Быстрая разработка и развёртывание
  • Проще отладка и мониторинг
  • Меньше инфраструктурных затрат
  • Легче поддерживать
  • Возможность миграции на микросервисы позже

⚡ Микросервисы (для масштабирования)

При росте более 50,000+ пользователей

  • Независимое масштабирование компонентов
  • Изоляция отказов
  • Гибкость в выборе технологий
  • Но: сложнее в разработке и поддержке
  • Требует опыта работы с распределёнными системами

5.3. Выбор: Webhook vs Polling

Критерий Long Polling Webhook
Латентность ⚠️ Средняя (зависит от интервала polling) ✅ Низкая (instant push)
Нагрузка на сервер ⚠️ Постоянные запросы к Telegram API ✅ Только входящие события
Сложность настройки ✅ Простая (не нужен SSL/домен) ⚠️ Требует SSL сертификат и домен
Масштабируемость ❌ Ограничена ✅ Высокая
Для production ⚠️ Подходит для малых ботов ✅ Рекомендуется для высоконагруженных

🎯 Рекомендация

Для MVP: Начать с Long Polling для быстрого прототипирования

Для production: Использовать Webhook для лучшей производительности и масштабируемости

Пример: Получение информации о слотах

import aiohttp

async def get_timeslots(client_id: str, api_key: str, warehouse_id: int):
    url = "https://api-seller.ozon.ru/v1/draft/timeslot/info"
    headers = {
        "Client-Id": client_id,
        "Api-Key": api_key,
        "Content-Type": "application/json"
    }
    payload = {
        "warehouse_id": warehouse_id,
        "delivery_type": "fbo"
    }

    async with aiohttp.ClientSession() as session:
        async with session.post(url, json=payload, headers=headers) as response:
            if response.status == 200:
                data = await response.json()
                return data.get("result", {}).get("timeslots", [])
            else:
                raise Exception(f"API Error: {response.status}")

  • Кэширование: Кэшировать список складов и справочную информацию

⚠️ Обработка ошибок API

  • 401/403: Помечаем магазин «ошибка ключей», отключаем трекинг, уведомляем пользователя
  • 429 (Too Many Requests): Экспоненциальный ретрай с джиттером, бэк-офф до 30 мин
  • 5xx (Server Errors): Экспоненциальный ретрай с джиттером, бэк-офф до 30 мин
  • Timeout: Повторная попытка с увеличенным таймаутом

7.5. Безопасность API ключей

🔐 Критически важно

  • Хранить API ключи в зашифрованном виде в БД (AES-256 или KMS/DPAPI/аналог)
  • Использовать переменные окружения для мастер-ключа шифрования
  • Никогда не логировать API ключи
  • Реализовать ротацию ключей
  • Использовать HTTPS для всех соединений
  • Rate-limits per store для защиты от злоупотреблений

  • За 3 дня до истечения отправляется предупреждающее уведомление

Состояния заказа:

  • FOUND: Бронь подтверждена, трекинг отключён
  • PAUSED: Пользователь остановил отслеживание, фон не опрашивает
  • FAILED: Превышен лимит ретраев/ошибка API, уведомление с причиной

12.2. Retry стратегия

Политика повторных попыток:

  • 1-я попытка: немедленно
  • 2-я попытка: через 1 мин
  • 3-я попытка: через 5 мин
  • 4-я попытка: через 15 мин
  • 5-я попытка: через 30 мин
  • После 5 попыток: переход в состояние FAILED, уведомление пользователя

Джиттер: ±10% от времени ожидания для предотвращения синхронизированных запросов

13. Нефункциональные требования

13.1. Доступность и надёжность

  • Доступность: 99.5% в месяц (допустимый даунтайм ~3.6 часа/месяц)
  • RTO (Recovery Time Objective): ≤ 30 минут
  • RPO (Recovery Point Objective): ≤ 15 минут
  • Резервное копирование: Ежедневные бэкапы БД, хранение 30 дней

13.2. Производительность

  • Пропускная способность: ≥ 1000 активных заказов при опросе каждые 10 мин
  • Латентность API Ozon: P50 < 500ms, P95 < 2s, P99 < 5s
  • Время отклика бота: < 1 секунды на команду пользователя
  • Параллельные воркеры: Масштабируемое количество worker'ов для проверки слотов

13.3. Безопасность

  • Шифрование API ключей: AES-256 или использование KMS (AWS KMS, Azure Key Vault, и т.д.)
  • Аудит действий: Логирование всех операций с поставками и оплатами
  • Ограничение доступа: Principle of Least Privilege для БД и сервисов
  • Rate limiting per store: Максимум 100 запросов/мин на магазин
  • HTTPS: Все внешние соединения только через HTTPS
  • Защита от SSRF: Валидация всех URL перед запросами

13.4. Логирование и мониторинг

  • Структурированные логи: JSON формат с корреляцией по requestId
  • Уровни логирования: DEBUG (dev), INFO (prod), WARN, ERROR
  • Метрики:
    • Успех/ошибка бронирований (rate, count)
    • Латентность API запросов (histogram)
    • Квоты API (gauge)
    • Активные пользователи (gauge)
    • Выручка (counter)
  • Алерты:
    • Пик ошибок 5xx/429 (> 10% за 5 мин)
    • Доступность < 99% за час
    • Очередь задач > 1000 элементов
    • Worker'ы не работают > 5 минут

13.5. Масштабируемость

  • Горизонтальное масштабирование: Worker'ы, веб-сервер, БД (read replicas)
  • Кэширование: Redis для FSM state, сессий, справочников
  • Очереди: RabbitMQ/Redis для задач проверки слотов
  • Load Balancing: Распределение нагрузки между инстансами

  • Поддержка: Нужна круглосуточная техподдержка
  • Этика: Споры вокруг справедливости автоматизации бронирования

19.3. Рекомендации

  1. Начать с MVP: Фокус на мониторинг и уведомления, без агрессивного автобронирования
  2. Легальность: Проконсультироваться с юристами относительно ToS Ozon
  3. Конкурентное преимущество: Найти уникальную ценность (лучший UX, аналитика, ML-прогнозы)
  4. Пользовательские отзывы: Тесная работа с ранними пользователями для Product-Market Fit
  5. Партнёрства: Рассмотреть интеграцию с ERP системами для продавцов
